**WD-XL Lubrifont**

# Technical Tidbits

## Drawing the glyphs

The Chinese characters in this font have a width of 765, the em-box is set at <0 855 765 -145>, and the character face bounding box is set at <49 814 716 -104> (xMin, yMax, xMax, yMin). Most rounded corners have a radius of 30 or 35. Every square box has a 45° cut at the bottom right (if the bottom left has a turn but the right does not, the left is cut instead); for the cut triangle, the legs (width, height) have a length of 70 and the base (longest side) a length of around 99. The thickest stroke width is 94.

The bounding box values above are encoded in the `BASE` (baseline) table starting from v2.100. The width and height of the em-box (and their halves, the en) are also set in the font through the **advance width** of various spaces. `emspace` (U+2003, also `ideographicspace` U+3000) uses the em-width of 765, which lets it sit in a grid with Chinese hanzi; `enspace` (U+2002) uses half the em-width, 382. `emquad` (U+2001) uses the em-height of 1000; `enquad` (U+2000) uses half the em-height, 500.

The Latin characters in this font are proportional width. The vertical bounding range is <710 -220> (yMax, yMin) and the x-height is 485. Rounded corners have a radius of 40; for the cut triangle, the legs (width, height) have a length of 73 and the base (longest side) a length of around 103. The thickest stroke width is 92.

> Values above are for reference only.

## Preparing the source fonts

This font is made in FontLab 7. v1.0 used the font file generated by FontLab directly as the release font; from v2.0 the fonts are officially built with AFDKO. Even with this change in release method, the source font file `HuaYou-Regular.vfc` did not require major changes. FontLab can hold several masters in one file, and each master can be exported as a separate layer.

In v1.0, the released font used the "OpenType TT" export preset in FontLab, and the source files were exported with the "UFO Package" preset. The default information stored in the source file is for the SC version; before exporting the TC version, the name entries have to be changed to the TC version in the Tables window, part of the code for SC vertical typesetting has to be removed in the Features window, and the Codepages in Font Info are changed from 936 Simplified Chinese to 950 Traditional Chinese.

In v2.0, to speed up the merging process, empty layers are added to every glyph for every master before exporting, so that glyphs that do not need switching have an empty layer in place. If you do not want to add empty layers and just export all layers directly, set the `is_override_only = ` option in `merge-font.py` to False when merging; the code will then compare the glyphs of the two fonts to see whether they are the same, which takes longer. When exporting, the "OpenType TT" preset must be changed to untick every option under Outlines (e.g. Remove overlaps, Nodes at extremes, Clean up), to avoid the two fonts being exported with slightly different points because of the simplify/clean-up calculations, which would copy the same glyph twice.

## Writing `smpl`/`trad` code

As a testing font, this font implements the Simplified/Traditional Chinese conversion features defined in OpenType, `smpl` and `trad`. `smpl` defines conversion from Traditional to Simplified Chinese (or Japanese kyūjitai to shinjitai), while `trad` defines conversion from Simplified to Traditional Chinese (or Japanese shinjitai to kyūjitai). The related code is stored in `sources/smpl-trad-conv`.

This feature requires a **single-character** conversion table. We use the Wikipedia conversion table (https://phabricator.wikimedia.org/source/mediawiki/browse/master/includes/languages/data/ZhConversion.php) to make one-to-one and one-to-many mapping files: `sc-tc-1-1.txt`, `sc-tc-1-m.txt`, `tc-sc-1-1.txt` and `tc-sc-1-m.txt`. Before running `opentype-generate.py` or `csv-generate.py`, the `font-source` file path needs to be changed to a text file listing the Chinese characters in the given font. Feature code generated by `opentype-generate.py` can be pasted into FontLab directly, which is how it was used in v1.0; files generated by `csv-generate.py` are used from v2.0 by `split_simp_trad.py`/`split_simp_trad_cid.py` to separate the SC and TC versions, which changes the mapped glyph for SC and TC. (Python files with `cid` in the name are used after converting the font to CID-keyed.)

## Merging the fonts (v2.000)

This font takes 2 (actually 3) sets of regional glyphs, merges them into a central glyph database and then maps them to Unicode as required. This allows the same glyph database to be used for two regional fonts, while also allowing glyph changes within the same font. The pseudocode for the program is saved in `makeotf_from2font.txt`, finally realised after one year.

`merge_font.py` is the main code. It uses the `ttx` program to export the glyphs of both fonts and compare them. `ttx` is a tool to convert font files into a human-readable format, in this case XML; a similar tool is `otfcc`, which exports JSON. When merging, characters with the same Unicode code point but two different regional glyphs are placed consecutively, but two code points sharing the same glyph are not checked (this might be updated in future).

With help from ZERO ([@Skr-ZERO](https://github.com/Skr-ZERO)), this font includes a third region: JP. Since Japanese support was not planned for this font, these glyphs (~700) are appended at the end of the font, but no features use them. The glyphs currently added are made for JIS83, and a JP version is possible in future.

Files generated by `merge_font.py` are as follows (in the order the code generates them):

* XML dump of each font
* HuaYou-base.ttx
* AI0_HuaYou.txt *(all information about CID keys is stored here)*
* map_HuaYou.txt
* cmap_SC.txt
* cmap_TC.txt
* feature_gsub_SC_to_TC.fea
* feature_gsub_TC_to_SC.fea
* convert_SC_TC.txt
* convert_SC_JP.txt
* HuaYou.ttx

Files that are prepared beforehand (in the order the code uses them):

* WD-XLLubrifont-(region).ttf
* huayou-override-name.txt *(optional)*
* huayou-override-uni.txt *(optional)*

When `merge_font.py` has finished, `HuaYou.ttx` is merged into the template file `HuaYou-base.ttx` and saved as `HuaYou-src.ttx`; converting this text file back to the font file `HuaYou-src.ttf` with `ttx` completes this section.

## Merging the fonts (v2.001)

In version 2.001, with substantial help from ZERO ([@Skr-ZERO](https://github.com/Skr-ZERO)), this font gained basic Japanese support such as JIS90 and JIS2004 (the previous version added some JIS83 glyphs). The code to merge the fonts is now `merge_font_use_mergeFonts.py`. It no longer generates an XML font file; instead it uses `mergeFonts` to extract the glyphs of each region and then merge them into a new font, which is used in the next steps (`font.pfa`).

Files generated by `merge_font_use_mergeFonts.py` are as follows (in the order the code generates them):

* XML dump of each font
* AI0_HuaYou.txt *(all information about CID keys is stored here)*
* map_HuaYou.txt
* cmap_SC.txt
* cmap_TC.txt
* cmap_JP90.txt
* cmap_JP04.txt
* feature_gsub_to_SC.fea
* feature_gsub_to_TC.fea
* feature_gsub_to_JP83.fea
* feature_gsub_to_JP90.fea
* feature_gsub_to_JP04.fea
* map_SC.txt
* map_TC.txt
* map_JP83.txt
* map_JP90.txt
* map_JP04.txt
* comparison_HuaYou.txt

Files that are prepared beforehand (in the order the code uses them):

* WD-XLLubrifont-(region).ttf
* huayou-override-name.txt *(optional)*
* huayou-override-uni.txt *(optional)*
* jp90-override.txt *(optional)*
* jp04-override.txt *(optional)*

When this is done, the glyph outlines are extracted with the following commands:

* `tx -t1 .\WD-XLLubrifont-Regular.ttf tempfont_SC.pfa`
* `tx -t1 .\WD-XLLubrifont-Trad.ttf tempfont_TC.pfa`
* `tx -t1 .\WD-XLLubrifont-JP83.ttf tempfont_JP83.pfa`
* `tx -t1 .\WD-XLLubrifont-JP90.ttf tempfont_JP90.pfa`
* `tx -t1 .\WD-XLLubrifont-JP04.ttf tempfont_JP04.pfa`

The `-t1` parameter tells the program to extract only the glyph outlines and no other font information; the second parameter is the original font file name and the third is the output file name.

After that, the following command renames the glyphs of each font according to their source region and merges them into a single font source file `font.pfa` for the next step.

`mergeFonts font.pfa map_SC.txt tempfont_SC.pfa map_TC.txt tempfont_TC.pfa map_JP83.txt tempfont_JP83.pfa map_JP90.txt tempfont_JP90.pfa map_JP04.txt tempfont_JP04.pfa`

The first parameter is the output file name `font.pfa`; the following parameters come in pairs: `map_(region).txt` stores the list of glyphs to be renamed, and `tempfont_(region).pfa` is the glyph file extracted in the previous step. The format of `map_(region).txt` is as follows:

```
mergeFonts
new_name   orig_name
uni4E00-SC  uni4E00
```

## Making the final font

### Converting files to CID names

After the merge above, every glyph has been given a unique number, the CID, which can be looked up in `AI0_HuaYou.txt` or `map_HuaYou.txt`. As the final font's feature code (such as OpenType) needs the final CIDs, the prewritten features have to be converted from glyph names to CIDs. The prewritten feature code is in `HuaYou-feature-main.fea` (based on v1.0), and the program that converts the names is `fea_convert_name2cid.py`, which generates `HuaYou-feature-CID.fea`.

Unicode also provides Variation Selectors (VS), and setting up VS requires the final CIDs too, so the Python code `UVS_parser.py` converts the VS table `UVS_sequence` to `UVS_sequence_CID`.

The Simplified/Traditional conversion features `smpl` and `trad` are made with `split_simp_trad_cid.py` as described above.

### Preparing files for making the font

`cmap_SC.txt` and `cmap_TC.txt` need to be in the right format, so the section below in `cmap.raw` is replaced with the contents of the two TXT files.

```
0 begincidchar
==INSERT HERE==
endcidchar
```

Below are the prepared font-related files:

* cidfontinfo-SC
* cidfontinfo-TC
* cmap.raw
* feature_SC.fea
* feature_TC.fea
* FontMenuNameDB
* HuaYou-feature-main.fea *(needs converting to CID-keyed)*
* HuaYou-feature-template.fea *(template for `feature_SC.fea` and `feature_TC.fea`, not used when building)*
* UVS_sequence *(needs converting to CID-keyed)*

## Building the font

The following explains the files used and their purpose, in order. The examples use the SC version.

1. `tx -t1 HuaYou-src.ttf font.pfa`

### v2.000

This step extracts the glyph data, with their glyph names, from `HuaYou-src.ttf` and saves it in `font.pfa`.

### v2.001

Use the steps in "Merging the fonts (v2.001)" above to make `font.pfa`.

2. `mergeFonts -cid cidfontinfo-SC cidfont-SC.ps map_HuaYou.txt font.pfa`

This step uses 3 files, `cidfontinfo-SC`, `map_HuaYou.txt` and `font.pfa` from the previous step, to make `cidfont-SC.ps`. `cidfontinfo-SC` stores information about the font (e.g. name, weight, version); `map_HuaYou.txt` maps each glyph name to a unique identifier number, the CID. `cidfont-SC.ps` is a very basic font file that stores only the CID-ordered glyph list and basic font information.

3. (This font skips this step) `psautohint -a -o cidfont-SC.ps cidfont-SC.raw`

This step requires editing `cidfont-SC.raw` with a hex editor beforehand to write `BlueValues` indicating the zones used. The step adds hinting information to `cidfont-SC.raw` and produces `cidfont-SC.ps`. If this step is skipped, renaming `cidfont-SC.raw` to `cidfont-SC.ps` is enough.

4. `makeotf -f cidfont-SC.ps -omitMacNames -mf FontMenuNameDB -ff feature_SC.fea -cs 25 -r -ch cmap_SC.txt -ci UVS_sequence_CID`

The files used in this step:

* `-f cidfont-SC.ps`: the basic font generated in the previous step.
* `-mf FontMenuNameDB`: font name settings file.
* `-ff feature_SC.fea`: OpenType feature code.
* `-ch cmap_SC.txt`: CID-to-Unicode mapping file, ensuring glyphs are mapped to the correct Unicode characters.
* `-ci UVS_sequence_CID`: Variation Selector mapping table.

The settings used in this step:

* `-omitMacNames`: omit the Mac-specific name entries, unifying how the name is displayed.
* `-cs 25`: set the script of the Mac cmap; 25 is Simplified Chinese, 2 is Traditional Chinese.
* `-osv 5`: set the OS/2 table version to the latest, 5.
* `-osbOn 6`: turn on bit 6 of OS/2.fsSelection, marking the Regular weight.
* `-r`: release mode.

5. `sfntedit -d DSIG .\WD-XLLubrifontSC-Regular.otf`

This step removes the digital signature (`DSIG`) from the font. Word 2016 and later do not require a digital signature to use OTF fonts, and Google Fonts advises against adding one (even an empty one), so the signature is deleted.

### 2.100

[Continued from step 5 above]

6. Add primary design language/script (`dlng`) and supported language/script (`slng`) metadata to the `meta` table.

7. Use `otf2ttf` to convert to TTF format, then change the vertical metrics of the TTF files to meet the new Google Fonts CJK font metric requirements.

The font is now packaged.

## Merge to TTC font

`otf2otc -t CFF`` =0 -o WD-XLLubrifont.ttc WD-XLLubrifontSC-Regular.otf WD-XLLubrifontTC-Regular.otf`

This step merges the font files into one TTC font file. As the largest table (`CFF `) differs slightly between the fonts, sharing of that table has to be forced. Note that there is a space after `CFF `, and `otf2otc` currently does not support quotation marks (see https://github.com/adobe-type-tools/afdko/issues/1442), so in Windows PowerShell a backtick (\`) is needed to escape the space.

## Patch scripts (v2.200, v2.300)

The characters and glyph changes added in v2.200 and v2.300 did not go through the merge process above; they were made by Python scripts in `sources/` that edit the font files directly. Every new glyph is constructed from glyphs already in the font (e.g. Ѓ = Г + acute), so the scripts work both on the TrueType source (named glyphs) and on the CID-keyed OTF/TTF release files (new glyphs are appended as CID 18082 onwards; existing CIDs and OpenType features are unchanged). All scripts are safe to re-run: files that are already patched are skipped.

Run them in this order (requires `fonttools` and `skia-pathops`):

1. `add_macedonian_cyrillic.py` — Macedonian Cyrillic `ЃѓЅѕЈјЉљЊњЌќЏџЀѐЍѝ`
2. `add_extra_glyphs.py` — Serbian/Croatian letters `ĆćČčĐđЂђЋћ`, technical symbols, superscripts/subscripts, fractions
3. `dotted_zero.py` — dotted zero `0⁰₀０`
4. `diagonal_seven.py` — diagonal seven `7７⁷₇⅞`
5. `add_mark_anchors.py` — `mark` anchors for Cyrillic letters and `ĆćČčĐđ`
6. `add_ukrainian_belarusian.py` — Ukrainian and Belarusian `ЄєІіЇїҐґЎў` (v2.300; run `add_mark_anchors.py` again afterwards)
7. `respace.py` — corrects the side bearings of Latin and Cyrillic letters (accented letters follow their base, mark anchors move with the outlines)
8. `autokern.py` — kerning: `py autokern.py measure ../fonts/OTF/WD-XLLubrifontTC-Regular.otf kerning.txt` measures the outlines and writes `kerning.txt` (classes, class pairs, exceptions); `py autokern.py apply kerning.txt <fonts>` adds it to the release fonts as a `kern` feature. It also needs `freetype-py` and `uharfbuzz`. The kerning is not added to the TrueType source, because the full build generates GPOS from the feature files; after a full rebuild, run `apply` on the built fonts.
9. `track.py` — opens up the overall letter spacing: `py track.py 12 <fonts>` adds 12 units to both sides of Western letters, digits and punctuation (and 24 to the word space); CJK and full-width glyphs are not touched. Applied after v2.300.

```
cd sources
py add_macedonian_cyrillic.py WD-XLLubrifont-Regular.ttf ../fonts/OTF/*.otf ../fonts/TTF/*.ttf
(repeat for the other scripts)
otf2otc -t "CFF =0" -o ../fonts/WD-XLLubrifont.ttc ../fonts/OTF/WD-XLLubrifontSC-Regular.otf ../fonts/OTF/WD-XLLubrifontTC-Regular.otf ../fonts/OTF/WD-XLLubrifontJPS-Regular.otf ../fonts/OTF/WD-XLLubrifontJPN-Regular.otf
```

### How the spacing and kerning were measured

Each glyph is rendered at 1 unit = 1 pixel, and its left and right profiles (the distance from the edge of the advance box to the ink) are taken every few units of height.

* **Spacing (`respace.py`):** the average white space at each side over the letter body is compared with the straight letters (н п и, Н П И H N U); 70% of the difference is applied, open sides are not taken below 10 units, and differences under 5 units are ignored.
* **Kerning (`autokern.py`):** for each pair, the white gap over the heights where both glyphs have ink is compared with that of нн; 60% of the difference is applied, but no two shapes come closer than 40 units at any height, accents included. Values below 20 units are dropped. Base letters with similar kerning share a class, accented letters join their base letter's class, and pairs that differ from their class (usually an accent that would clash) get exceptions.

> Note: if the full merge process is run again later, `WD-XLLubrifont-Regular.ttf` already contains the new glyphs, but CIDs will be renumbered, so the feature code must be regenerated as described above.
